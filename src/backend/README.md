# Backend execution boundary

A backend is one TypeScript file with its own file ID, linked from a page by `<link rel="af-backend" href="…/af/v1/ids/<id>" data-af-name="<name>">`. This opt-in local Docker adapter compiles and executes it. It never falls back to a host process. The server owns authorization and persistence; this module owns execution and validates its immutable input.

```ts
import { gql } from "@afbin/apollo"; // also: pinned npm packages ("pg@8.13.1"), node:* built-ins

export const typeDefs = gql`
  type Query { greeting: String! }
  type Mutation { rename(name: String!): String! @auth(role: EDITOR) }
`;
export default {
  Query: {
    greeting(args, principal) {
      return `Hello ${principal.subject ?? "guest"}`;
    },
  },
  Mutation: { rename: ({ name }) => name },
};
```

`af-module.ts` reads `typeDefs` without running the file (Node's built-in type stripping plus `acorn`, both present in the production image): it must be a string or a `gql` template without `${…}`. Imports may be `@afbin/apollo`, `node:*`/`cloudflare:*` built-ins, and npm packages pinned to an exact version (`pg@8.13.1`, `@scope/pkg@1.0.0/sub`); an unpinned package is refused with the fix in the message, and paths, URLs and dynamic imports are refused (`packages.ts` `importKind`). Compilation maps `@afbin/apollo` to a built-in shim whose `gql` returns the template string. The platform supplies `directive @auth(signedIn: Boolean, role: Role) on FIELD_DEFINITION` and `enum Role { VIEWER EDITOR OWNER }` to every file.

`af-files.ts` is the server port: `compile()` checks and compiles the files a publish carries (outside the database transaction), `record()` stores an immutable version per compiled file and the page version's links (inside it), and `createBackendRoutes()` serves `GET /api/files/:id/backends` and `POST /api/files/:id/graphql`. A version is a digest of the file's source and schema, so an unchanged file keeps its version across saves, image rebuilds and runtime upgrades. A failed call keeps the fixed GraphQL message and adds `extensions.code` (the sanitized host code, `recompile_failed`, or `internal`), and the server logs one line with the page ID, backend ID, field and code. A page's backends run for every viewer who can open the page, signed in or not; `@auth` decides what each may call. `src/graphql/af-namespaces.ts` composes the linked files under their names, checks `@auth` and approval before invoking, runs mutation fields one at a time in the order written, and reports an outcome per field. `af-schema.sql` holds the tables; the server runs it after its own schema.

`createBackendHost()` exposes only `compile(source, signal)` and `invoke({deployment, principal, input: {field,args}, env, reuse, signal?, capabilityHandler?})`. `env` and the reuse decision are required: `{kind:"file", scope:{owner,fileId}}` uses platform-loaded file authority; `{kind:"one-shot"}` explicitly forbids warm reuse. Every adapter forwards this envelope, and authenticated remote frames reject missing or malformed dispositions. Trusted capability handlers must settle their owned work after abort: invocation and host cleanup await actual handler settlement, so an uncooperative handler keeps shutdown pending. The per-call protocol owner blocks new dispatch and late replies, enforces capability budgets and drains handlers; the work owner controls admission, cancellation and shutdown sequencing; the sandbox pool owns exclusive leases, capacity (including pending creation), idle timers and all retirement barriers. Compilation returns an immutable `CompiledBackend`; `af-files.ts` records it as an immutable version of the file. It pins source, compiled JavaScript, SDL and resolver names by their own hashes, and records its runtime as `BACKEND_RUNTIME` (`deployment.ts`: the workerd, esbuild and frame-protocol generation) plus the image ID it was compiled on. Compatibility is by generation, not image ID: an invoke runs on the image the host is configured with whenever the deployment's generation is current, so rebuilding or redeploying the executor image leaves every backend working; a recorded image that differs is only logged at debug level (`NODE_DEBUG=pagegi`). Bump `BACKEND_RUNTIME` whenever the container changes what a compiled bundle needs from its executor. A deployment of another generation no longer verifies; the server recompiles its stored source on the first call, checks the schema is unchanged, stores the new deployment under the same version and runs it, or settles the field `rejected` with `extensions.code` `recompile_failed` (or the transient host code, such as `backend_busy`). Deployments stored before versions named only source and schema keep their old version and still verify. Protocol 3 (the current generation) bundles npm modules, passes `env` bindings and gives invocations the public network; deployments of protocols 1 and 2 are recompiled on first use like any older generation. A deployment also records a `lockfile`: every npm module it was built from (the pinned import as written, or the esm.sh URL a package imported) → the exact esm.sh URL and its sha256. It is a record for audit and reproduction; the bundle is what runs.

## npm packages (`packages.ts`)

Compilation runs in a sandbox without network, so the execution service fetches packages first: for each pinned import it requests `https://esm.sh/<pkg>@<version>?target=esnext&bundle&conditions=workerd` (the Workers build: `pg` and `postgres` open sockets through `cloudflare:sockets`), follows esm.sh's `x-esm-path` header to the real module, and fetches every esm.sh module that one imports, until only `node:*` and `cloudflare:*` imports remain (esm.sh writes `cloudflare:sockets` as `/cloudflare:sockets?…`, which the bundler rewrites to the bare name). Fetches retry transient failures (network, 429, 5xx) three times, time out after 10 s each, count the body as it streams (1 MiB per module), never leave esm.sh, and are cached in the service for an hour, at most 32 MiB; a cached fetch is shared by concurrent compiles and started without any caller's signal, so one cancelled compile never fails another. A compile has 20 s for all its packages (`PACKAGE_BUDGET_MS`), at most 64 modules and 1 MiB in all, counted as each module arrives; a package that stalls past the budget is named in the `build_rejected` detail. The module texts travel in the compile frame; `container/bundle.mjs` resolves imports only from them and bundles with esbuild, and its gate then allows only `node:*`/`cloudflare:*` imports, static or literal dynamic. Any failure is `build_rejected` with a `detail` naming the package, which the publish response shows. Unit tests inject the fetcher (`fetchModule`); nothing in CI reaches esm.sh.

## Secrets and network

`env` (the backend file owner's secrets, `af-files.ts`) reaches the resolver as its fourth argument. The host checks it (at most 64 names matching `[A-Z][A-Z0-9_]{0,63}`, values 1–4096 bytes without NUL) and sends it in the `serve` frame; the supervisor writes each value to a file in the sandbox's temporary directory and binds it with `text = embed`, so no value is quoted into the config. `nodejs_compat_do_not_populate_process_env` keeps bindings out of `process.env`, and `entry.mjs` withholds the capability service binding from `env`. Because bindings are fixed when a sandbox starts, the warm-sandbox key includes a digest of `env`: two owners' identical files never share a sandbox, and a changed secret starts a new one.

Invocations run on the Docker network `pagegi-sandbox` (`sandboxNetwork`, `PAGEGI_SANDBOX_NETWORK`; `none` disables it), which the host checks once when it is built (creating it if missing) as an IPv4-only bridge (`--ipv6=false`) named `pagegi-sbx` with inter-container traffic disabled; a network of that name with other settings is refused (logged, calls `backend_unavailable`) and sandboxes are never attached to it, and one removed under a running host is checked and recreated once when a container create reports it missing; Docker isolates it from the Compose project network, so sandboxes cannot reach Postgres, the app or the execution service. Inside, workerd's network service allows `public` and denies `private` and `local`, for `fetch` and `connect()` alike and for names that resolve to such addresses; https trusts Node's root CAs, written to `/app/ca.pem` at image build (the slim image has no CA store). Compilation still runs with `--network=none`. On the production host `deploy/receive.sh` installs the kernel-level backstop as `/usr/local/sbin/pagegi-sandbox-egress`, run on every deployment and by `pagegi-sandbox-egress.service` at boot and after Docker restarts (`deploy/execution-service.md`): traffic from `pagegi-sbx` to private, link-local and loopback ranges and to the host itself is dropped, except DNS to the host's resolvers. Those rules are IPv4 (iptables); the bridge has no IPv6.

## The store (`caps.store`)

Each backend file has one JSON document the platform keeps in `af_backend_stores`, shared by every page and viewer that calls the file. Resolvers call `caps.store.get()` (`{ value, version }`) and `caps.store.set(next, { expected })` (compare-and-swap on the version; a conflict throws an error with `code: "conflict"`). The isolate never touches the database: `entry.mjs` sends `{ kind: "store", operation }` capability requests, and `af-files.ts` passes a per-call handler from `af-store.ts` bound to the file being called. With an operator's resource configuration, `capability-authority.ts` routes store requests to that handler and everything else to connectors. Anonymous callers may use the store (the platform owns it) but never connectors. A document is limited to 60 KB of JSON so it fits the 64 KiB capability frames. Protocol 1 deployments run without capabilities and so without the store. Each successful store commit also appends a durable `backend_store_invalidations` event in the same transaction; conflicts append nothing. App processes consume this outbox independently to notify current pages using the backend file, across saved deployment versions. Event allocation holds a transaction lock until commit so a sequence cursor cannot skip a late commit.

## Execution contract

Compilation uses a fresh Docker container per compile. Invocation uses a warm container per backend version, image and `env`: the supervisor's `serve` mode keeps one workerd running and answers one `invoke` frame at a time; the host keeps it for `warmIdleMs` (60 s) after its last call, removes it after a failed call or on `close()`, and makes room by removing the least recently used. Every container has 256 MiB memory, no swap, 0.5 CPU, 64 processes, no host mounts, a read-only root, a 16 MiB temporary filesystem, UID 10001, dropped capabilities, no-new-privileges and Docker seccomp. Compilation has no network; invocation has the sandbox bridge described above. The supervisor checks those controls before handling a request (no interface but `lo` for a compile, at most one more for a lambda). Compiled bundles may import only `node:*`/`cloudflare:*` built-ins; anything else, including computed dynamic imports, is rejected. Only JSON crosses bounded stdio; backend console output is not forwarded. Capability requests use a workerd service binding to a supervisor Unix socket and bounded duplex newline frames to the host; no connector driver, platform credential or host mount enters the child; the owner's secrets enter only as `env` bindings.

Source is limited to 256 KiB, compiled JavaScript to 1 MiB, and invocation arguments/principal and returned JSON to 64 KiB. The default execution watchdog is 10 seconds for compilation (after the npm fetches) and 10 seconds for invocation, including container setup; the execution service's own deadline is 40 seconds per request (above a compile's 20 s package budget plus its watchdog); it starts when the call is admitted. Cleanup follows the watchdog and has separate bounded Docker command waits. Eight operations may run concurrently (`maxConcurrent`); a call arriving at capacity waits in arrival order up to `admitWaitMs` (default 2 s) for a slot and is only then refused `backend_busy`, and cancellation while waiting leaves the queue. Up to sixteen sandboxes stay warm (`maxWarm`, never fewer than `maxConcurrent`). Each invocation permits at most 100 capability calls, 8 pending calls, 64 KiB per request/result, and 1 MiB cumulative capability request/result data. Handler failures expose a generic rejection with unknown outcome and never forward diagnostics or retry writes, with one exception: a store write over 60 KB (checked in `entry.mjs` before the frame leaves the sandbox, and again by `af-store.ts`) throws an error with code `store_limit` inside the resolver, which may catch it; uncaught, the call fails `store_limit` and the field settles `rejected` since nothing was saved. `entry.mjs` reports that code only for errors it created itself, so a resolver cannot forge it. A call the sandbox reports failed (`backend_rejected`: the resolver threw or returned non-JSON) carries the thrown message's first line, at most 200 characters, as `BackendHostError.detail`; `af-namespaces.ts` shows it as `extensions.detail` to the page owner only. Cancellation, deadlines, and cleanup abort the handler signal. Source and SDL syntax budgets bound host-side validation too.

Cancellation during container creation waits for the create acknowledgement before removal. Every acknowledged container is forcibly removed and checked absent before returning. Missing create acknowledgement or failed cleanup reports `cleanup_failed` and closes admission on that host instance; it never reports verified cleanup from an ambiguous daemon response. The host then heals itself: the container is listed as a suspect, and on the next call (or at once, in the background) the host removes every suspect again, checks each absent, lists the containers carrying its label and generated name pattern and confirms no suspect remains; only then does it admit calls again. A proof that fails keeps the host closed and is retried on the next call after `recoveryRetryMs` (default 5 s). One log line marks each transition (closed, reopened). `close()` while a suspect remains reports `cleanup_failed`. No claim is made that an unreachable daemon can be remotely controlled.

Root field names must be unique across Query and Mutation, and their resolver groups must match the SDL exactly. Subscriptions are outside this contract. Return values must be JSON data: holes, accessors, cycles, undefined, nonfinite numbers and non-JSON objects are rejected. Application source, compiled JavaScript and diagnostics belong to owner-only deployment records, not the public schema response.

## Reproduce

```sh
docker build -t pagegi-backend:local src/backend/container
node --import tsx --test test/backend-deployment.unit.test.ts test/backend-process.local.test.ts test/backend-container.isolate.test.ts test/v2/backends/lambdas.isolate.test.ts
```

`PAGEGI_BACKEND_IMAGE` selects another image for these tests (the tag is shared by every checkout on one Docker engine). The process seam tests deterministically delay create acknowledgements and split every byte of UTF-8 responses. The real-container tests exercise compilation, principal snapshots, warm sandboxes, `env` bindings and an empty `process.env`, refused private addresses, npm packages from an injected fetcher, source imports, CPU deadlines, kernel OOM, malformed outputs, cancellation and recovery; `PAGEGI_TEST_INTERNET=1` adds a real esm.sh package and a public https call. The supervisor enforces the configured cgroup and filesystem checks on every call. These tests validate this adapter on the available Docker engine. In production it runs inside the `execution` service of `compose.yaml` ([`deploy/execution-service.md`](../../deploy/execution-service.md)), the one service with the Docker socket; the app service never gets it.

Dataset mutation refusals carry `dataset_mutation_rejected` only after validation before execution or a successfully recorded terminal refusal. The sandbox tracks that trusted error separately from authored error codes; GraphQL settles the field as rejected. Inflight attempts, transport failures and failed refusal receipts remain unknown. This additive protocol-4 code safely degrades to unknown on an older entry image; update the image to expose definite refusals. Read `dataset_changed` remains a separate refresh signal.

# Backend execution service

Backend files are compiled and run by the `execution` service of [`compose.yaml`](../compose.yaml): the same image as the app, started with `node src/backend/execution-main.ts`. It is the one service with the host's Docker socket, because it creates the per-request sandbox containers described in [`src/backend/README.md`](../src/backend/README.md); that is host-level authority, so the service holds no application credential (it has no `env_file`), publishes no port, and admits a request only with the shared transport secret. The app never gets the socket.

The app reaches it at `http://execution:8788/v1/execute` on the project network (`PAGEGI_EXECUTION_ENDPOINT`, set in the Compose file, which overrides any `PAGEGI_EXECUTION_SOCKET` in `.env.production`). Both read the secret from `execution-secret/transport-secret` beside the Compose file: at least 32 printable characters, mode 0400, owned by the container user (`1000`). The app waits for the execution service to be healthy, so an execution service that cannot start fails the deployment and `deploy/receive.sh` restores the previous images.

Requests without the secret are answered 401 before any body is read; the service's healthcheck relies on that. Default request execution is bounded to 40 seconds (a compile spends at most 20 seconds fetching its npm packages from esm.sh, then has a 10-second sandbox watchdog; an invocation's sandbox deadline is 10 seconds) and sixteen concurrent streams (above the container host's eight running calls plus its short admission queue, which is what governs), with 2.5 MB frames and 256 frames per stream, and at most eight pending capability calls. Capability IDs must be positive unique integers within each invocation; malformed UTF-8, duplicate IDs and excess pending calls close the stream and abort active handlers. The container host keeps its stricter source, output, CPU and memory limits. Capabilities are serviced by the application over the invocation stream with its authenticated principal and deployment-scoped broker; the execution service cannot nominate a callback URL, and redirects are never followed.

Before admitting any request, the service removes the backend containers a previous controller on this engine left behind (`src/backend/reaper.ts`): at most sixteen containers carrying the `pagegi.backend=1` label and the generated container name, each verified before any is removed, and none may remain afterwards. A cleanup that cannot be verified keeps the service closed, which the deployment sees as an unhealthy service. Nothing else on the engine is touched. Do not run independent controllers or integration tests sharing that label on the same engine.

The sandbox image is `pagegi-backend:<sha>`, built by the deployment from the release's `src/backend/container` and passed as `PAGEGI_BACKEND_IMAGE`; the execution service runs it with `--pull=never`, so the image must exist on the engine. The service needs the Docker group's numeric ID (`DOCKER_GID`, default 986) to reach the socket. Shutdown stops admission, cancels active invocations and capability handlers, and waits for container cleanup; the service exits unsuccessfully if cleanup fails or its 20-second watchdog expires, and Compose gives it 25 seconds.

For a dedicated execution host instead, run the same entry point with `PAGEGI_EXECUTION_BIND`/`PAGEGI_EXECUTION_PORT` or `PAGEGI_EXECUTION_SOCKET` and point the app's `PAGEGI_EXECUTION_ENDPOINT` or `PAGEGI_EXECUTION_SOCKET` at it: HTTP alone does not encrypt the bearer secret, so a separate host needs an authenticated encrypted private network or mutually authenticated TLS.

Lambdas run on the Docker network `pagegi-sandbox` (`PAGEGI_SANDBOX_NETWORK` in the Compose file), which the service checks when it starts and creates if missing: an IPv4-only bridge (`--ipv6=false`) named `pagegi-sbx` with inter-container traffic disabled. A network of that name with other settings is refused and lambdas stay unavailable until it is removed; one removed while the service runs (`docker network prune`) is recreated on the next call; it is not the project network, so sandboxes cannot reach Postgres, the app or this service. workerd inside each sandbox allows public addresses only. `deploy/receive.sh` installs iptables (IPv4) rules on `pagegi-sbx` (no traffic to the host, to private, loopback or link-local ranges, or anywhere but DNS on the host's resolvers); the bridge has no IPv6, so there is nothing for ip6tables to filter. Every deployment writes the rules to `/usr/local/sbin/pagegi-sandbox-egress`, installs and enables the oneshot `pagegi-sandbox-egress.service` and runs the script. The unit runs after `docker.service` at boot and, being `PartOf=` and `WantedBy=docker.service`, again whenever Docker restarts or starts, so the rules survive reboots and Docker restarts; `systemctl restart pagegi-sandbox-egress` reapplies them by hand (for example after the host's resolvers change). Stopping the unit leaves the rules in place. The service fetches npm packages from `https://esm.sh` when it compiles, so it needs outbound HTTPS.

Raster processing shares the authenticated execution transport at
`POST /v1/image-process`. Only the execution controller creates decoder jobs;
`PAGEGI_IMAGE_PROCESSOR_IMAGE` selects its fixed, release-versioned image. The app
receives neither a native decoder nor the Docker socket. Jobs have one admission
slot, no queue, a 15-second deadline and separate image container ownership labels.
Startup verifies cleanup of these dedicated containers before listening; shutdown
aborts incomplete uploads and waits for verified job removal.

Both release receivers build the decoder image from the release source and keep
`current-image-processor-image` and `previous-image-processor-image`. Successful
rollouts pin the selected image in Compose `.env`; failed rollouts restore its
previous pointer with the app and backend composition. CI caches this image using
its source tree, lockfile, Dockerfile, Docker ignore rules and execution platform.

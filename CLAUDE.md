## ⚠️ PRIMARY WORKING STYLE: TEST-DRIVEN DEVELOPMENT

**This is non-negotiable and SUPER IMPORTANT — do not deviate. Every feature and refactor MUST follow this exact order. Do NOT implement first and back-fill tests.**

### The required order (every change)
0. **Module design is important (Ousterhout)** — before any code, decide which modules are new and which change, and how each one's interface/boundary is designed or affected. Prefer deep modules: a narrow interface hiding real complexity. State this decision up front.
1. **Contracts first** — define robust types, interfaces, and method signatures. Reuse existing types; no duplication; keep it elegant.
2. **Tests second** — write tests that fully exercise the ACTUAL behavior (not just helpers), and **confirm they FAIL (red) before implementing**. A green test that was never red is decoration.
3. **Implementation third** — write the code until the tests pass (green).
4. **Run the full suite** to confirm no regressions.
5. **Commit and push to the PR.**
6. **Verify on the running dev server** — drive the real flow with curl (mint → create → open the link) or the browser; don't assume, check.

### Refactoring — Blue → Red → Blue
1. Identify tests covering existing behaviour — they must pass (blue).
2. Break the old implementation and confirm tests fail (red). This proves the tests guard the behaviour.
3. Re-implement until all tests pass (blue). Run the full suite, push, verify on the dev server.

> A green test that was never red is not a test — it's decoration. When asked "did you do TDD / verify end-to-end?", answer honestly.

### Pull Requests

**Raise every PR with NO description body.** Do not write a summary, a "what/why", a test plan, or any descriptive comment on the PR — open it with an empty body (`gh pr create --body ""`). The title alone stands.

## Planning: de-risk in the plan, not in the build

A plan is a list of claims. Before any phase is dispatched, every claim it rests on is VALIDATED in the
planning stage itself — by running something, never by reasoning alone:

- **Every assumption gets a script.** "The packages link via workspaces", "the app can boot as the restricted
  role", "the native module survives a lean install", "the header survives the adapter" — each is a throwaway
  program or a curl against a real container, run during planning, with the observed output pasted into the
  plan. A claim that was not run is not validated; the plan marks it ASSUMED, in those letters, until it is.
- **The plan carries a risk register.** One row per risk: what breaks, how it was measured, its status
  (MEASURED / MITIGATED / ASSUMED / OPEN) and the evidence. The register is updated after every phase; an
  ASSUMED row that reaches implementation is a planning failure.
- **Milestones are cut FROM the risk register, riskiest first — this rule ranks equal with validation.** Write the
  register, sort it, and the first milestone IS its top rows; never draw up phases by feature or by folder and
  check them against the risks afterwards. The FIRST phase holds the work whose failure would change
  the plan the most — the deepest unknown, the ugliest dependency, the cutover shape — so it is proven or
  disproven while changing course is still cheap. "Riskiest" means *plan-changing if wrong*, not *hardest to
  build*; polish, docs and mechanical moves go last.
- **Milestones are checkable.** Each phase ends with a thing that can be booted, curled or measured
  (a running stack, a green gate, a rehearsed cutover), never with "the code is written".

## Working model: define → scope → delegate → review

Two roles, never mixed in one session:

- **The orchestrator** (the main session the user talks to) owns the plan. It decides the module design
  (Ousterhout — which modules, which boundaries, stated up front), writes the contracts and the CORE
  tests that define "done", validates and de-risks with scripts and throwaway programs (it MUST — never
  assert what can be run), and then hands each phase to a delegated agent as ONE large, fully specified
  task: design, contracts, the tests that must be RED first, the deletion list, the constraints, the
  definition of done, the report format. It does not implement the phase itself. When the report comes
  back it REVIEWS — modules, contracts, tests (red-before-green evidence), implementation, suite counts,
  the dev-server verification — and sends the agent back with specifics when something is off. A phase
  counts only after that review. The plan document is updated after every phase.
  **After every review — re-read the work DAG and dispatch.** The moment a subagent's work is reviewed and handled
  (merged, or sent back), the orchestrator looks at the whole DAG again — every project, not just the one that
  finished — and starts every node whose dependencies are now met, on its own agent and port block. It never waits
  for the user to say "go" on work that is already planned and unblocked; it asks only for decisions that are the
  user's (scope, money, production). "Nothing is running" while a plan has a startable node is an orchestrator failure.
  **Review means RE-RUNNING, never reading.** A report is a claim. The orchestrator independently: runs
  `tsc --noEmit` and the full suite in the agent's tree and compares the counts to the report; re-runs
  at least one test the report says was red, with the implementation reverted, to see it red; checks the
  diff against the brief file by file (scope creep in, deletions out); re-does the dev-server / compose
  walk with its own curl; and checks the ports the agent bound against its block; and runs `gh pr checks` — the PR's CI and CodeQL are part of
  every phase's definition of done, and a red check nobody looked at is a failed review. A claim the orchestrator
  could not reproduce is treated as false, and the agent is told exactly which.
- **A delegated agent** implements exactly the brief it was given, in this repo, following the TDD order
  above, and reports with evidence (what was seen red, counts, commands run, the commit). It NEVER
  delegates further and never widens its scope; if the brief is wrong or blocked, it says so in the
  report instead of improvising.

If you are reading this as a delegated agent: you are the implementer. Do the work, do not spawn agents.

### Parallel delegation

Several agents may run at once, on the SAME laptop, and must never share a checkout or a port:

- **The orchestrator hands each agent a SEEDED worktree — the agent never makes its own.**
  `node scripts/agent-worktree.mjs --phase <p> --brief <file> [--secrets] [--install]` (a downstream repo that
  embeds this one as a submodule runs the same script from there, with `--pin-submodule`)
  creates `../<repo>-<phase>` on branch `split-<phase>` from `simple-split`, writes the port block to `.env`
  (which `npm run dev` loads) with fresh `AUTH__SECRET`/`AUTH__SECRET` and the mail-sink URL, and
  puts the brief at `.agent/BRIEF.md` with the block appended — brief, env and plan are ONE source. `.agent/`
  and `.env` can never be committed. Before dispatch the orchestrator SEEDS the tree with the phase's contracts,
  its core tests (RED at handoff — the agent's report cites the red it inherited) and skeleton modules
  (signatures, doc-comments, `throw new Error('<phase>: implement')` bodies), committed on the sub-branch so
  review is `git log` from the seed. The agent's prompt is then short: the tree, and "read `.agent/BRIEF.md`".
  Each worktree has its own `node_modules`, PGLite dir, object dir, compose project name and image tags. The
  agent commits to its sub-branch; the ORCHESTRATOR merges into `simple-split` at review — still one PR per
  repo. `--remove` tears a tree down. Never two agents in one tree.
- **One 100-port block per agent, at an even hundred: 5000–5099, 5200–5299, 5400–5499 …** — blocks never
  touch, and a port derived by "+100" from one block lands in the gap. Ask the machine, never guess:
  `node scripts/port-block.mjs [--count N] [--env]` (`scripts/`; a block is free only if every port in it binds;
  `--env` prints it as the lines below, which `agent-worktree.mjs` writes into the tree's `.env` and brief):
  ```
  APP__PORT=<base>            APP__HMR_PORT=<base+1>      APP__PUBLIC_BASE_URL=http://localhost:<base>
  SQL__SERVICE_URL / BROWSER__SERVICE_URL / postgres / minio / compose host bindings: <base+10 …>
  ```
  `APP__HMR_PORT` defaults to `APP__PORT + 1` (`lib/config resolveHmrPort`); the origin defaults
  (``EXPORT__INTERNAL_ORIGIN`) follow `APP__PORT`; data dirs are relative paths.
- **The browser gates run in ONE agent at a time** (each gate binds a fixed mail-sink port): the agent that
  owns the app phase runs them; others run `npm test` only.
- **Dependencies decide what may run in parallel, not folders.** OSS phases are sequential (P1 → P2 → P3);
  what parallelises is work in the OTHER repo, or infra (Dockerfiles, CI, docs) beside code. Never split one
  phase across two agents that meet at the same seam (server.ts, identity, a shared test file).
- Practical ceiling on one laptop: 2–3 agents (Chromium gates and docker builds are the load).
- **A hand-made worktree needs `npm ci`, and its output must be read UNFILTERED.** `agent-worktree.mjs --install`
  does it; a tree made by hand has no `node_modules`, and a lockfile half-merge announces itself as
  `npm ci: Missing: <pkg> from lock file` in the middle of otherwise ordinary output. Grepping for "error"
  misses it.

### ADDING A TABLE OR A CONFIG NAME IS FIVE EDITS, NOT ONE

Measured in the assets spike, one guard at a time — a fifth appeared only after the fourth was fixed, and each
one is a guard doing its job. Adding `web_assets` + `ASSETS__MAX_BYTES_PER_TOKEN` left the suite red four ways
until all five were done:

1. `lib/schema.ts` — declare the table AND add it to `TABLES`.
2. `lib/__tests__/schema-ownership.test.ts` — add `'app.<table>'` to the literal.
3. `lib/__tests__/schema-sql-fresh.test.ts` — add it to the owners literal.
4. `npm run render:schema` — regenerates `SCHEMA.sql`, `roles.sql`, `grants.sql` (the deployment truth).
5. **`.env.example` AND `scripts/lib/setup-plan.mjs`** — the setup planner carries a BASE64 SNAPSHOT of
   `.env.example` (`ENV_EXAMPLE_BASE64`), and `scripts/__tests__/setup-plan.test.mjs` stays red until it is
   regenerated. Invisible until you hit it: fixing `.env.example` alone leaves the suite red with a different
   failure. A new app config name also has to be audited in `lib/config.ts` or `lean-closure.test.ts` names it.

### Coding agent lessons

Any headless coding harness can be the implementer: the handoff is the seeded worktree, the deliverable is
commits on `split-<phase>` plus `.agent/REPORT.md`, and the review is the same. Launch a non-Claude harness as
a BACKGROUND Bash command — its exit is the completion notification; there is no other channel. One line per
agent, learned by running it (keep this list current; add a line the first time a harness is used):
**IMPLEMENTER DEFAULT:** Opus 5 subagents (the Agent tool), unless the user asks for a specific harness for a task or a period — then use exactly what they named and go back to the default when they say so.

- **Claude (Agent tool, Opus 5)** — reports arrive as a task notification; it must still write `.agent/REPORT.md`
  like everyone else. It will run the browser gates if told to; only one agent may. RESUME: `SendMessage` to its agent id
  continues it with its full context (verified: it recalled a code word after finishing).
- **Codex (`codex exec`, 0.151)** — `codex exec -C <tree> -m gpt-5.6-sol -c model_reasoning_effort=high -c sandbox_workspace_write.network_access=true --approve-for-me "<prompt>" < /dev/null > .agent/RUN.log 2>&1`.
  `< /dev/null` is REQUIRED (it blocks on "Reading additional input from stdin" otherwise); `--approve-for-me`
  already implies the workspace-write sandbox and cannot be combined with `-s`; `--full-auto` no longer exists;
  `--dangerously-bypass-approvals-and-sandbox` is refused by the auto-mode classifier. The sandbox's NETWORK deny
  is what made loopback binds AND Docker fail inside it (`EPERM`; `docker ps` → denied — measured with
  `codex sandbox -c 'sandbox_mode="workspace-write"' -- <cmd>`): `-c sandbox_workspace_write.network_access=true`
  lifts only that — docker, loopback binds and `gh` then work, while writes outside the tree stay denied
  (measured 2026-08-31). Without it, socket-based tests must be re-run in the review, outside. RESUME: `codex exec resume <session id> "<prompt>"` — the id is the `session id:` line at the top of RUN.log (verified). Verdict from the first run: followed the TDD order, honest report, 6-file commit accepted.
- **pi (GLM-5.3 on Fireworks)** — `cd <tree> && FIREWORKS_API_KEY=… pi -p --session-id <phase> --model fireworks/accounts/fireworks/models/glm-5p3 "<prompt>" < /dev/null > .agent/RUN.log 2>&1`.
  RESUME: the same command with the same `--session-id` continues it (verified: code word recalled across two `-p` runs); `--no-session` would make it unresumable. A tool result carrying an IMAGE kills the run hard (Fireworks 400 "This model does not support image inputs" — no retry, run over) — and the image then sits in the session history, so the session is POISONED: resume re-sends it and dies the same way; finish with a fresh run. Tell it in the prompt to never screenshot. Reads CLAUDE.md by default (the evals pass `--no-context-files` to stop that; we do not). No MCP client. Runs with no sandbox, so the full suite runs inside it. Verdict from the first run: followed the TDD order, every claim reproduced on review (red, tsc, 1820-test suite); 4-file commit, equivalent to Codex's.
- **Every harness** — macOS has no `timeout`: cap a run with `gtimeout` or a `perl -e 'alarm N; exec @ARGV' --`
  wrapper. The permission rules that let the orchestrator launch them live in `.claude/settings.local.json`
  (gitignored), granted explicitly by the user. A run that exits with no `.agent/REPORT.md` is a failed run.
- **Every gate run — two ways to score the wrong thing.** WARM THE SPA with one throwaway browser load before the
  first gate: a cold Vite dep cache can leave that first load with two React copies and an empty `#root`, so the
  gate that happens to be first fails for a reason that is not in the product. And STOP A DEV SERVER BY PORT
  (`lsof -tiTCP:<port> -sTCP:LISTEN | xargs kill -9`), never by killing `npm run dev`: a boot that finds the port
  taken prints `Port … unavailable` and exits, and the gate then measures the OLD server — a pass that says
  nothing about the code just written.
- **Every merge — lockfile halves.** Two branches that each regenerated `package-lock.json` can merge with NO conflict
  into an invalid union (`npm ci`: "Missing: <pkg> from lock file") — local suites hide it because node_modules is
  already populated; only CI's `npm ci` sees it. After ANY merge touching the lockfile: `npm install --package-lock-only
  && npm ci --dry-run` before pushing.
- **Every harness — quota.** A Codex run that hits the OpenAI usage limit exits 0 with `ERROR: You've hit your usage limit` as the last lines of `RUN.log` and NO `.agent/REPORT.md`; the commits it made are fine but the brief is half-done. Measure the tree (tsc, seed tests, the image), then `codex exec resume <session id from RUN.log> "<the measured gaps>"` to continue WITH its memory (0.151); a fresh `codex exec` in the same tree also works and is cheaper when the old session was large (>150k tokens). Never restart from the seed. Beware: grepping RUN.log for `usage limit` also matches your own prompt — read the last lines.

## Project Overview

artifactbin is a tiny self-hosted artifact store: external coding agents
(Claude Code, Codex, …) publish self-contained documents over plain HTTP and
hand their user a shareable link. **There is no agent in this repo — it is pure
infra**; the DX centerpiece is `GET /docs`, a self-describing SKILLS TREE (`skills/`, one small markdown file per topic, the brief first) that
teaches any agent the whole protocol.

- **Stack**: Hono + Vite + React 19 + TypeScript. One full self-host image plus optional split service images; no ORM or migration framework.
- **Storage**: PGLite (embedded, default) or Postgres (`DATABASE_URL`).
- **Surface**: bearer-token JSON APIs (CRUD + versions/revert) + `/a/<id>` serving (+ pretty `/@username/...` URLs) + `GET /docs/*` (the skills tree; `/api` and the old `/docs/llm|markup|themes|templates|artifact-design` pages are RETIRED and 404 — see `lib/__tests__/no-dead-api-link.test.ts` and `no-dead-docs-address.test.ts`) + a small UI (home = artifact list, `/tokens` = token management/claiming, login/signup, CLI approve).
- **UI system**: Tailwind v4, terminal-graphite theme (dark default, `[data-theme='light']` palette, toggle persisted in `localStorage('mx_theme')` and stamped before paint by `web/index.html`). `components/` holds app chrome; `components/kit/` is the document kit the story runtime renders. `web/Shell.tsx` composes shared page chrome around the routed page outlet. Grow either layer only when a pattern repeats.

npm run eval -- --harness <name> --model <id> --api-key-env <VAR> [--mode fetched_skill+api_action|fetched_skill+mcp_action|installed_skill+api_action|installed_skill+mcp_action] [--label L] [--tasks x,y] [--deployment URL]

npm run eval -- --ci …   # the CI task set, exit code = verdict. A failed flow gets ONE more

The gates are discovered from disk, never listed by hand: a new `gate-*.mjs`
joins the set by existing. They FAN OUT OVER SERVERS, not over gates: what made
the set sequential was never the browser but the server — two gates sharing one
share a mint ceiling, a login door and a listing — so a worker gets its own
server (`--servers=N`: in-memory PGLite, its own object dir and port) and runs
its own gates one at a time. **The gates run in parallel by default; a serial
run is an explicit `--servers=1`, for debugging only.** The runner prints
`gates: N server(s), M gate(s)` before it starts and the wall-clock when it
ends, so a serial run is visible in any log. Booting is also the default
because a DEV server is not what CI runs: Vite's HMR websocket is on a second
port that the app's fixed `connect-src 'self'` CSP refuses, the SPA never
mounts, and 26 of 42 gates time out on a checkout where nothing is wrong
(measured, and the same 26 failed on a commit that had changed nothing).
34 gates went from ~25 minutes to ~3. Below that the
MACHINE is the floor — four workers on four vCPUs — so the set also SHARDS across
runners (`--shard=i/n`, `scripts/gates.shard.mjs`), balanced by each gate's
measured `timeoutMs` rather than by count, because app-flows is 75s and
annotations is 9s and a split by index hands one runner every slow gate. 40 gates
over two runners: ~192s to ~105s each. A gate that FAILS
under that load gets one more turn ALONE and is NAMED in the summary when it
passes there: four browsers on one machine can lose a race that is not a
broken contract, and a retry nobody is told about is how a real intermittent
bug hides. They need a running server (and, where they log in,
development mail written to their protected outbox), which is why `npm test` does not
run them — but CI DOES: the `browser gates (i/2)` matrix builds and runs the set
across TWO runners, four of its own servers each, and is part of the `test`
roll-up, so a
"guarded by `scripts/gate-…`" note in this file is enforced on every PR rather
than left to whoever remembered. A login code is read by the ADDRESS it was
sent to, never by arrival order: the relay copies every message to every sink,
which was harmless while one gate ran at a time and is a race now.

## Architecture

- **`services/contracts` + `services/utils` ARE THE SHARED SEAMS.** Contracts owns types and pure constants; utils owns signing, actor transport, HTTP helpers, doors and assembly. The app asks `actorOf(request)` first, so in-process and HTTP forwarding have one identity interface; the signed header is only the network fallback. Splitting these boundaries replaced the old monolithic contract/conformance package: services test their contracts directly over local and HTTP transports, and runtime code has one implementation of signing rather than two lookalikes.
- **NEXT IS GONE: the server is Hono, the pages are a Vite SPA.** `server.ts` boots ONE process — the proxy in front of `services/app/server/app.ts` (Hono), sharing one database; `npm run dev` runs it under tsx with Vite in middleware mode, with HMR on `APP__PORT + 1` by default (`APP__HMR_PORT` overrides), and the image runs the esbuild bundle `server.mjs` with the SPA prebuilt into `dist/web`. The route table is GENERATED from the filesystem the way Next derived it (`scripts/generate-routes.mjs` → `server/routes.generated.ts`, mounted by `server/api.ts`), so a new `app/**/route.ts` joins by existing and `server/__tests__/routes.test.ts` fails when the file is stale; handlers keep their `(Request, {params}) → Response` signature, so the in-process suite is unchanged. The reader/owner split that was `proxy.ts` middleware is now ordinary routing in `server/app.ts`, which also owns three rules the framework used to: an address the viewer may not read answers **404 as a STATUS** (not a 200 carrying a not-found page), the canonical address **heals with a 302** for a page viewer and never for a reader (the shared link is where they are served), and the app CSP is set here rather than by config. The app's own pages are `web/` (`App.tsx` routes, `Shell.tsx` chrome, `pages/*`), fed by `/api/page/{session,home,account,artifact/:id,profile/...}` — the endpoints answer what the page components used to compute, under the same ACL and the same uniform 404s; `test/helpers/pages.ts` gives the suite the old vocabulary (render | redirect | notFound) over them. Four things were learned by breaking them: `lib/request-context` (AsyncLocalStorage) replaces `next/headers` so `publicOrigin()` and analytics still see the request; `lib/navigation` and `lib/dynamic` replace `next/navigation`/`next/dynamic` with the same shapes; the browser bundle must hold NO server config (a bare `process.env` read in `lib/config` reached it through a browser-shared module, and the whole SPA died with `process is not defined` — `lib/ids-shape` and `lib/invite-param` exist to keep node crypto out of it); and **Tailwind's source detection is rooted at the BUILD's root**, which is `web/`, so `app/globals.css` names `@source "../components"` — without it the app chrome compiled to nothing and the document frame fell back to a bare 300×150 iframe. **A page is served WITH its data inlined** (`withBootstrap` → `web/bootstrap.ts`): the server answers the question the page would immediately ask and puts it in the HTML, so first paint is final geometry — no fetch round trip, no chrome settling, and a pretty URL carries BOTH answers (the resolution and the document page) because one missing answer is one visible settle.
- **A ROUTE'S HEADER OBJECT IS NOT A CONSTANT — the server writes into it.** `@hono/node-server` writes the computed `Content-Length` back INTO the object a route hands to `new Response(body, { headers })`, so a module-level constant becomes shared mutable state and every later response of that route announces the FIRST body's length. The browser drops those with `ERR_CONTENT_LENGTH_MISMATCH` and the keep-alive connection's framing is corrupt for whatever follows; curl reads what it is given and shows a perfectly good body, which is why it hides. It cost every live update in the product — `/a/<id>/events/frame` is fetched after each version ping, so a reader watching an agent, an editor beside a collaborator and a shared document's own stream all silently stopped adopting, and eight browser gates failed on this one line. Build the headers fresh per response. Pinned by `server/__tests__/content-length.test.ts`, which goes over a REAL socket — the mutation is in the writer, so a route tested by calling its exported function cannot see it.
- **ONE FORWARDER, ONE LIVE-STREAM OWNER.** `services/proxy` forwards unmatched requests to the app and does not maintain a second Postgres LISTEN relay. The app owns document events and their ACL, whether composition is in-process or the upstream is HTTP; removing the second stream path removed a configuration-dependent authorization seam.
- **REMOTE SQL** (`services/sql`): `SQL__SERVICE_URL` selects the HTTP client; unset selects the local engine registered by `server.ts`. Both implement the `@artifactbin/contracts` `SqlService` and run the same contract suite, so one-statement admission, bound params, interrupts and row caps cannot fork. The full image carries the local engine today; the standalone SQL image carries the service entry.
- **`services/proxy` IS PARTS, NOT A SECOND APP.** `proxyParts` declares ordered ownership and `createProxy` assembles it; `server.ts` composes proxy and Hono app in-process, while the same forwarder can use an HTTP upstream. The app owns all six token routes and the token table; the proxy resolves bearer/session/agent-cookie identity, enforces doors, hosts Better Auth and OAuth, then forwards an `Actor`. Better Auth options are pure and shared with the schema renderer; `actorOf(request)` is the app boundary, with the signed actor header only for a network hop. The lesson from the split was that route-prefix copies and duplicate token implementations drift; one ordered part list and one app-owned token surface do not.
- **THE RATE LIMITS ARE A FILE, AND THE FILE LIVES AT THE PROXY.** There is no door vocabulary and no `RATE_LIMITER__<NAME>_MAX` any more: every number is in a POLICY FILE, and adding a limit is editing a file rather than editing three packages. A **policy** is a budget (`max` per `window`, keyed `ip` | `actor` | `ip+actor` | `email`, `burst` multiplying `max` for a caller who proved a credential on the SAME bucket, `repeat: N` making a hit whose exact URL was already seen in the window cost `1/N`); a **route** (a method or list, a regex over the pathname, optionally exact `query` params) says which budgets apply where, FIRST MATCH WINS; `always` applies to every request first. All of a route's policies must allow, every one is counted in written order, and the FIRST refusal is what the 429 body and `door.denied` name. `browser_only: true` on a route refuses a non-browser BEFORE anything is counted, with the ladder body `services/proxy/src/parts.ts` owns — the flag only says WHICH routes carry it. Three files ship, differing only in the anonymous mint: `services/proxy/{default,selfhost,dev}_rate_limits.yml` (0 — production; 10 — self-host; 2000 — gates and `npm run dev`). `PROXY__RATE_LIMIT_CONFIG_FILE` picks one and is the ONLY rate-limit env name besides `RATE_LIMITER__TRUSTED_PROXY_HOPS`; unset means the closed default, found by walking up for `services/proxy/default_rate_limits.yml` (the one rule that holds in the source tree AND in both images, which bundle to different depths). The file is read ONCE, at boot, by `proxyParts`: a missing file, an unparseable one, an unknown policy name, a route with no policies, a regex that does not compile, an unknown key or a window that does not parse REFUSES THE BOOT naming the offending line — never a silent fallback to numbers nobody chose. A credential raises the same bucket ceiling; it never bypasses it. The proxy derives client IP once, is the ONE place a request is counted (`lib/__tests__/doors-one-place.test.ts`), and its own verdicts are the 429 and the `browser_only` 403; the app owns semantic quotas it alone can see. The limiter is per PROCESS, so two replicas each hold their own counters and the effective ceiling is `max × replicas`.
- **ENV NAMES ARE NAMESPACED — `MODULE__NAME`, ONE SPELLING.** `lib/config.ts` audits app settings; service `createEnv`/`readEnv` calls audit their own settings. `DATABASE_URL` and `S3_URL` remain conventional exceptions. Unknown names are reported and retired names fail loudly. `AUTH__SCHEMA` locates Better Auth tables, while `APP__SCHEMA` tells the proxy token reader where the app tables live; the generated `roles.sql`, `SCHEMA.sql`, and `grants.sql` are the deployment truth.
- **PAINT FIRST: A READER WAITS ON THE PAGE, NOT ON THE SQL** (`declarationsForRow` beside `dataflowForRow`). The served document carries its `<Value>`/`<Query>` DECLARATIONS and no rows — the server runs nothing — and the document fetches its own data through the transport its island already names. Measured on a production dashboard: 231 KB of a 365 KB page and ~90ms of a ~100ms render, all spent before the reader saw anything; after, TTFB 4.5s → 55ms locally and the page arrives at FINAL GEOMETRY, so nothing moves as the numbers land. The CAPTURE render (`chrome=0`) is the exception and must stay one: `/export` photographs that frame, and a photograph of a skeleton previews nothing. Three things this re-taught, each found by a browser gate and invisible to all 2,800 unit tests: an inline `<Value type="table">` carries its rows in the DECLARATION and the server was the one copying them into state (every chart bound to one drew nothing); `pending` must mean "not current" on BOTH sides or SSR renders "not busy" while hydration renders "busy" and React discards the whole server tree (#418); and `pending()` is a `useSyncExternalStore` snapshot, so returning a fresh `Set` per call span-locks the document's own event loop — no timers, no promise callbacks, on a page that otherwise looks fine. The store MARKS what needs running and the CALLER starts it (`store.start()`), because a framed document relays through the page and a message posted before the page is listening is not queued, it is gone. **An author's `<script>` still runs at the first commit, but `mx.data.get()` is empty for the round trip it takes to fetch rows — a script that needs them subscribes.** Holding the script until the data settled was tried first and is the wrong trade: in a frame the shell has just replaced, "settled" is a round trip away.
- **THE READER'S `<Value>` CHOICES TRAVEL IN THE LINK — `?$region=west`** (`lib/story/url-values.ts`, the ONLY place a URL becomes typed scalars or scalars become a URL; `lib/story-runtime/url-values-sync.ts` is the document's half). A dashboard's whole point is that the reader narrows it, so the address they then copy has to be the document they were looking at. `$name` is the document's OWN binding syntax, and the server's keys on `/a/<id>` (`key`, `chrome`, `edit`, `comment`, `v`) carry no `$` and a Value can never be named with one, so a selection cannot shadow them. A malformed link never throws and never blanks a document: an undeclared name, a table Value, a value the declared type refuses (judged by the publish door's OWN `scalarMatches`) or bytes that will not decode are simply not there — which is also why the pairs are split by hand ON THE WAY IN rather than by `URLSearchParams`, whose lenient `%E2` → U+FFFD would turn a truncated link into a real, wrong selection. Empty is null ("All", the way the dataflow spells it everywhere); only NON-DEFAULT values are written, so a document at rest has a plain address.
  - **THE SEED IS THE ISLAND'S `values` FIELD, NEVER `state` — or paint-first dies.** `state` present is how a capture and the editor's canvas say "the rows are already computed", so seeding a selection through it silently cancels the store's first run and leaves every chart on its skeleton (`lib/story-runtime/__tests__/store-paint-first.test.ts`). Precedence, lowest to highest: the declarations' defaults, a capture's state, then the URL. The CAPTURE (`chrome=0`) is the exception the paint-first rule already carves out — it is threaded into the run itself, because `/export` photographs a settled frame.
  - **THE WRITE-BACK IS ONE NARROW CAPABILITY, AND ORDER IS THE MECHANISM.** `HISTORY_PRELUDE` (`lib/story/document.ts`) runs in three beats: bind the native `replaceState`, THEN freeze the History API shut, and only THEN build `window.__mxValues` — frozen, non-writable, non-configurable — because every statement shares one fail-silent `try`, and a capability that throws in front of the freeze would leave the document with a fully writable History API and nobody told. It takes `$` params and nothing else: no path, no host, no hash (both read fresh at call time), keys that are not plain value names dropped, and the search rebuilt through `URLSearchParams` ON THE WAY OUT so a `#` or `&` inside a value is a character and never a delimiter (`$` alone is written back literally — the point is a link a person can read). FRAMED, none of that applies — the `location` a framed document reaches is the FRAME's (`/a/<id>/raw?edit=1`, which nobody can copy), so it posts `mx:values` up the signed channel and the PAGE writes, re-deriving the address from the flow IT holds. Debounced, and compared against what was last said: a store notifies for rows landing and queries going busy, and an address rewritten on each is churn in the reader's own back button. The iframe `src` is seeded ONCE and never follows the live address — a `src` write NAVIGATES the frame, so it would reload the whole document on every pick while looking entirely correct.
  - **THE EXPORT'S CACHE KEY IS THE VALIDATED, NON-DEFAULT SELECTION** (`urlSelection`, hashed into `exportStoreKey`), never the raw params: both cache layers are keyed by artifact VERSION — which is what lets one render serve every unfurl with no invalidation ever run — so a raw token gave one document unlimited distinct keys for byte-identical renders, a cache-fill vector behind a door that bounds the RATE and not the total. Anything the document would ignore (undeclared, invalid, already the default) collapses onto the default shot. The CARD is deliberately excluded: an unfurl is of the DOCUMENT, and one reader's filter is not what the next person should meet in a preview. Guarded by `lib/story/__tests__/url-values.test.ts` + `history-prelude.test.ts`, `__tests__/url-values-serving.test.ts`, `lib/story-runtime/__tests__/store-paint-first.test.ts` and `scripts/gate-dataflow.mjs` (a real browser: the picks reach the address bar, the link reaches the document, and the frame is never reloaded).
- **AN UPLOAD IS MADE FIT TO READ AT PUBLISH** (`lib/images/optimise.ts`, behind the ONE door every upload already comes through — `storeImageContent`, shared by the picker, paste/drop and the URL importer). Capped at `MAX_IMAGE_EDGE`, converted to WebP, measured, and given a ~100-byte blur placeholder. At publish rather than on first read because the first reader of a document is the person its author just handed the link to, and they must not pay for an encode — publish is already where the Tailwind compile, the SQL dry run and the webfont fetch happen. The floor under every rule is **never return something worse than what was given**: a conversion that comes out bigger is discarded, bytes that will not decode pass through untouched, and SVG (text, scales) and animated GIF (would be frozen) are not touched at all. WebP alone — universal since 2020, so a second format buys only an `Accept` negotiation and a `Vary` header, which is the part that goes wrong with caches. The DIMENSIONS ride the ref map (`lib/story/ref-data`, which both render paths consume) so markup reserves the box and the page stops jumping; an author's own sizing wins. **The cap is the lever, not the format**: on the 1.04 MB production photograph (1700px, already under it) WebP saves 11% at q82 and 21% at q78; a phone photo at 4000px loses three quarters of its pixels. Images stored before this were converted once, in place, and the one-shot script that did it is gone with them.
- **THE LIVE STREAM CARRIES PINGS; THE FRAME IS STATELESS AND COMPLETE** (`lib/story/frame.ts`, `app/a/[id]/events/{frame,authorize}`). `/a/<id>/events` used to build the whole frame — parse, SSR nodes, DuckDB — PER CONNECTION on every wakeup, and omitted the stylesheet "when unchanged since the last frame on this connection", which made the frame uncacheable and the stream unrelayable by anything blind to content. Now the stream says only `{editId, version, by}` (and `event: data {datasets}` / `event: annotations {}` — pings too; the annotator's page refetches its annotation list), and a client fetches `GET /a/<id>/events/frame`: the parsed body, the compiled CSS (ALWAYS — there is no "last time"), the author CSS, the design, the declarations' SIGNATURE and their FLOW — and NEVER dataflow rows: a client that sees the signature move re-runs its queries through the transport it already has (`store.replaceFlow({flow})` with no state dirties every query), one that sees it unchanged keeps what it has. Cached per (id, edit_id) — two hundred readers cost one build per version. Same read ACL as the page and `raw` (uniform 404), and the served document's CSP admits it as a separate path-exact `connect-src` entry (CSP matches a path without a trailing slash exactly, so `/events` never covered `/events/frame` — the live-reader gate found that, the unit suite could not). `authorize` answers a RELAY blind to content: the channels to follow — the document's and every dataset it reads or writes — re-derived per version. The wakeup itself is an interface (`lib/story/wakeup.ts`: LISTEN through the app's db handle in-process today; a proxy-held LISTEN later). Guarded by `__tests__/live-frame.test.ts` and the three live gates.
- **A SHARE HAS THREE ROLES, AND SHARES RESOLVE TO ACCOUNTS.** `viewer | commenter | editor` (`lib/share-roles`): a commenter may read and annotate (open threads, reply, resolve — the anchor stamp runs under `annotationScope`, which widens the edit scope for that one write) and may NOT edit; `useCanEditArtifact` is owner|editor, `useCanAnnotateArtifact` is not-reader — the first shell derived "can edit" as "not a reader" and handed a commenter the edit button the moment the role existed (`components/__tests__/artifact-role-hooks.ui.test.tsx`; `gate-collab-edit` has a commenter leg). `artifact_shares.user_id` is stamped on the FIRST match of a signed-in person (`resolveSharesFor`); predicates match by user id first and by email only while unresolved, so a share follows the account through an email change and an old invite to an address the person no longer has stops matching (`__tests__/share-resolution.test.ts`). Email is an attribute, never an identity key.
- **THE OBJECT STORE ANSWERS BYTES OR AN ERROR — NEVER "EMPTY".** `ObjectUnavailable` (`lib/object-store`) is what `get` throws on ANY failure: missing object and denied read are deliberately undistinguished, because THE DB IS THE ONLY INDEX — every key the app reads (`ref:` images, dataset rows, webfonts via the `webfonts` table, `isKnownWebFontFile` before the store is asked) is one a row recorded, so a store that will not give the bytes is corruption or broken credentials, and both must be loud: `image-store`/`dataset-store` no longer degrade to `null`/`[]`, `raw` answers `503 asset unavailable` for an image it cannot serve, `/webfonts` still fails closed to 404. No `s3:ListBucket`, ever (the permission S3 wants before it says 404 rather than 403). There is no boot canary any more — the put/get probe went with the Next instrumentation hook that ran it, and the boot path is now `server.ts main()` after `getDb()`, whose only housekeeping is the trash sweep — so a bad `S3_URL` announces itself on the first read, loudly, by the rule above rather than at startup. **`getStream` IS THE SECOND READ, AND IT IS DELIBERATELY OUTSIDE THE CACHE.** `get` is right for everything the one read cache exists for — a dataset, a `ref:` image, a webfont are read many times and small enough to hold. A PDF is neither: measured, one 25 MB object through `get` is +25 MB of RSS for the life of the response AND would be admitted to a 32 MB cache, evicting essentially everything the product depends on to hold one file streamed to one reader once. So the large-object tier reads through `getStream` — nothing buffered whole, nothing cached, not even counted — with an INCLUSIVE `range` so a viewer seeking inside a PDF costs exactly the bytes it asked for (`/a/<id>/raw` answers `Accept-Ranges`, a real `206`, and `416` past the end). A missing object still raises `ObjectUnavailable` from the returned promise, never an empty stream.
- **REMOTE CHROMIUM** (`services/browser`): `BROWSER__SERVICE_URL` selects the HTTP client; unset selects the local Playwright implementation registered by `server.ts`. ADD COLUMN IF NOT EXISTS`), applied on every boot. **Additive DDL is the entire migration story** — to add a column, declare it and it appears on next boot; never write a migration script.

- `lib/tokens.ts` / `lib/auth.ts` — bearer tokens `mx_<256 bits>`: shown once, sha256-only storage, soft revoke. All bearer failures are a **uniform 401**; admin-secret failures a **uniform 404**; an unreachable id is a **uniform 404** — never reveal existence. Tokens may be **anonymous** (`user_id NULL`, self-minted via `POST /api/tokens/anonymous`, IP rate-limited) or user-owned.
  - **A CREDENTIAL RAISES THE MINT CEILING, IT NEVER REMOVES IT** (`anonMintRateLimited`, `HOLDER_MINT_MULTIPLIER`). The valve is for a stranger opening the door, so refusing a real user's tenth document of the hour is the failure it exists to avoid — but `/api/start` implemented "not a stranger" as "not counted", and a token costs exactly ONE mint, so the whole valve was one request deep (measured: one token published well past the hourly cap). A holder now gets `ANON_MINT_MAX * HOLDER_MINT_MULTIPLIER` on the **same per-IP bucket** — same bucket is the load-bearing half, since a separate holder bucket would be the old hole with an extra step: the stranger mints that bought the token would not count against what the token then spends. - `lib/users.ts` / `lib/codes.ts` / `auth.ts` — accounts (the SENDING half moved with identity: the proxy owns login and its mailer, `services/proxy/src/{auth/human,mail}.ts`; the app's own `lib/email.ts` went with it). Login is **email + a one-time code**, the only way in: no passwords, no bcrypt, no reset flow, and sign-up and sign-in are the same act (a verified code for an unknown address creates it). Codes are stored **hashed, server-side, single-use**, capped at 5 guesses, and are NEVER returned to the caller — the tempting stateless shortcut (a signed blob carrying the code) is an account takeover, since a JWT is signed but not encrypted. The mechanics live in `lib/codes.ts` — ONE `codes` table for every one-time secret (`kind`: login | oauth | future), the only writer/reader; a new flow is a new `kind` string, never a new table (`claimByHash` for high-entropy secrets, `claimBySubject` for guessable ones). `EMAIL__RESEND_API_KEY` is REQUIRED; there is deliberately no log-the-code fallback. Better Auth database sessions are owned by the proxy. **Claiming** (`claimToken`) attaches an anonymous token + backfills its artifacts to a user; artifacts stamp `user_id` from their token at publish time. The dashboard lists by `user_id`.
- **OAuth 2.1 for `/mcp` is the PROXY's** (`services/proxy/src/identity/oauth.ts`; the app's `lib/oauth.ts` was its pre-split twin and is gone — only the `WWW-Authenticate` breadcrumb was still live, and it now lives in the CONTRACT, which is the one place both sides can share it). It is a **delivery mechanism for `mx_` tokens, not a second token system**: `/oauth/token` ends in `mintToken`, so `resolveToken`/revoke/claim are untouched. PKCE codes are rows in the shared `codes` table (5-min TTL, hashed, single-use) — see `lib/codes.ts` below. `/oauth/authorize` is a ROUTE (not a page) so it can set anti-clickjacking headers middleware-free; there is **no guest grant**: a token minted here goes to the CLIENT and is never shown to the human, so nothing could ever claim what it publishes. Zero-friction entry survives where the human holds the token (`POST /api/tokens/anonymous`, `/api/start`). The grant is CSRF-guarded by the SameSite=Lax session cookie, and `auth()` is caught and failed CLOSED. The `/mcp` 401 carries `WWW-Authenticate` pointing at `/.well-known/oauth-protected-resource` — that header starts the whole client dance.
- `lib/object-store/` — where artifact BYTES live, behind `put`/`get`/`delete` on a key. Configured by ONE `S3_URL` (credentials + bucket + top-level folder), parsed in `url.ts`; unset, it falls back to the local filesystem so a laptop and CI need no external service. Keys are content-addressed (`dataset/<sha256>`), so re-uploading the same file costs one object. The URL's path is `bucket/prefix`, which is how one bucket serves `artifacts` (production) and `artifacts-dev` (local) without a dev machine being able to write over production. **The store has no existence question, and the IAM user has no `s3:ListBucket` — by design.** Without ListBucket S3 answers a missing key with 403, so the store alone cannot tell "missing" from "denied"; it does not need to, because THE DB IS THE ONLY INDEX: every key the app reads (`ref:` images, dataset rows, webfonts via the `webfonts` table) is checked against its DB row first, and an unknown key is a 404 from the DB before the store is asked. A store failure on a DB-referenced key is therefore an ERROR — a row promising bytes the store will not give is corruption or broken credentials, and both must be loud, never a silent `null`/`[]`. The `/webfonts` route, the one read whose key comes from the CALLER, fails closed to 404 on ANY read error. The contract is pinned by `lib/object-store/__tests__/store.test.ts`, whose S3 leg needs `TEST_S3_URL`.
- `lib/story/dataset-store.ts` — dataset rows go to the object store and the row keeps `meta.objectKey`; `content` stays empty. A 27 MB sheet in a TEXT column would be read and parsed on every render and every `/edits` write. A row without a key has NO rows ([]) — the pre-object-store inline fallback is retired (pre-production, no back-compat).
- **WRITABLE DATASETS — a `<Mutation>` is a `<Query>` that writes** (`lib/story/dataset-mutate.ts`). A dataset carries a WRITE ACL beside its read one: `artifacts.access` = `read` (the default, and every dataset that predates it) or `readwrite`. Two separate questions — `visibility` is who may READ the artifact, `access` is who may CHANGE it through a document — and neither implies the other. The declaration is the third Helmet data child (`lib/story/dataflow parseMutationDecl`): one statement, INSERT/UPDATE/DELETE by TYPE (`lib/sql/engine` write mode, which registers ONLY the target table so the DML can name nothing else), exactly ONE `ref_<id>` — the dataset it writes — and `$params` bound, never interpolated. `<Button run="$name">` runs it; `mx.mutate(name, values?)` is the script's fourth verb.
  - **The write is a CAS on `edit_id`, and a lost CAS just re-runs.** That is sound here in a way it never was for text: a splice is POSITIONAL, so replaying it on a changed base can land where its author never meant, while an `insert … values` replayed against the winner's rows lands after them and an `update … where` re-applied to current rows is exactly what was asked. So the rebase is free, no write is lost, and there is no lock — writes to one dataset serialize on its own edit_id, writes to different datasets never meet. Everything else is the paths that existed: the blob is content-addressed (an idempotent write costs no object), the previous state archives on the edit protocol's coalescing rule (so `revert` works on DATA), and the row's own channel is NOTIFYed.
  - **Who may write** (`canWriteDataset`, re-checked on EVERY call, never trusted from publish): anyone who can READ a document may run the mutations it DECLARES — supplying scalar values only, since the SQL is the stored one — and the write performs as the DOCUMENT's owner (`writerFor`). The target must be `readwrite` AND the publisher's OWN: the link-readable fallback that lets any document READ a public dataset deliberately does not extend to writes, because "anyone may read this" has never meant "anyone may append to it". Both refusals land at PUBLISH with the fix named.
  - **A write is LIVE, and that closes an older gap too**: `/a/<id>/events` now also LISTENs on every dataset the document reads or writes (`datasetsForDocument`, re-parsed from the source — mutation targets count) (re-derived per frame, subscribed at CONNECT and BEFORE announcing a new version — a document that starts reading a dataset must be subscribed by the time its reader can see the query) and emits a named `data` frame carrying no rows, only which dataset moved. The store marks the queries reading it dirty (`queriesReadingDatasets`) and re-runs them through the transport it already has — so the reader's scroll, their `<Value>` choices and every other chart survive, and an agent's dataset PUT now reaches the documents charting it, which it never did before. The writer's own tab invalidates directly, so the click that adds a row is the click that redraws the chart. `STORY_DATA_EVENT` lives in the react-free contract, NOT beside the route: a client module importing a value from a route handler pulls `next/headers` into the browser bundle (a build failure, not a size regression). Guarded by `scripts/gate-live-data.mjs` (three browser contexts, no reloads) — which also covers the RELAY write, since a document inside a parent is opaque-origin and cannot present a session: that path is chosen by "am I framed", not by visibility, so an owner viewing their own document exercises exactly the code a private document's readers use.

Guarded by `__tests__/mutate-csrf.test.ts`, which tests BOTH credentials — the hole lived in the untested one.

- **`lib/web-ingest/` — IMPORT, NEVER HOTLINK.** The ONE place this app fetches a caller-supplied URL, so the SSRF posture is audited once. A web URL is a SOURCE: the server fetches it at publish time, stores a copy, and the document references the copy — which is why nothing here needed a CSP change, a runtime proxy, or a reader's IP reaching a third party, and why a document cannot rot when its source host dies. `guard.ts` is the pure boundary (private/reserved/link-local ranges, WHATWG parsing so `0x7f000001` normalizes before the check, credentials and non-default ports refused; the metadata IP stays forbidden even under the dev switch that admits loopback); `fetch.ts` is node:https with a **custom `lookup`**, so the address the guard approves IS the address the socket dials — no resolve-then-connect race — re-run on every redirect hop (≤3), body STREAMED against a byte cap and destroyed at it, one deadline over the whole chain; `sniff.ts` types the bytes, because a remote `Content-Type` is attacker-controlled and a dead image link serves html (`sniffAssetType`/`sniffImageType`/`sniffFontType`, and the PDF tier's `%PDF-` — a file that is not a PDF is `400 invalid_pdf` however it is named). Consumers: `image.ts` (composed with the SAME `storeImageContent` uploads run, so caps and types cannot fork), `lib/data-ingest/csv-url.ts`, `lib/webfonts`, and now `lib/web-assets.ts` — every URL-kept image, self-hosted FACE and imported PDF comes through here too, so the SSRF posture is still audited in one place. Rate-limited per identity by ATTEMPT (`webIngestRateLimited`) — probing is the abuse shape and probes fail, so successes would be the wrong thing to count — and the BYTES are charged to the first importer's account (`lib/asset-quota`), once, because the copy is global: a reference is free, and billing every referrer would make a popular URL progressively more expensive for everyone. A refresh pays the same cap; a document's `{id}` refresh is charged to the document's OWNER (`writerFor`), not to the editor who asked.
  - **THE AUTHOR'S URL STAYS IN THE SOURCE; ONLY THE SERVED COPY IS SWAPPED.** An `<img src="https://…">` — or a `<Video poster>`, a `<File src>` naming a PDF, or an `@font-face { src: url(…) }` in the author's own `<style>` — is IMPORTED at publish and the source is left exactly as written. Same stance as the `<p><div>` rule (agents emit web URLs constantly, and a refusal an agent cannot act on is a dead end), and the opposite MECHANISM: the earlier door rewrote the attribute to `ref:<id>`, which minted an image artifact nobody asked for and handed the author back markup they did not recognise. Four modules, one each: `lib/story/external-images.ts` is the PURE half — which positions hold a URL (one parse per read, because every read of every document asks it); `lib/web-assets.ts` is the global `url → object` cache, fetched once through `lib/web-ingest` and `lib/images/optimise`, one row per canonical URL, FIRST IMPORTER WINS so a second document naming it fetches, stores and is charged nothing; `lib/asset-quota.ts` charges the stored bytes to the ACCOUNT (a cap on the token alone is bypassed by minting a second one; an anonymous token is keyed on itself); `lib/story/asset-url.ts` is the SERVE-TIME mapping, above the Helmet split beside `fixHtmlNesting`, so the SSR string, the island, the preloads and the live frame cannot disagree about an address. A URL that will not fetch is a WARNING, never a refused publish — `asset_warnings: [{code, url, fix}]`, its own reply key beside the dataset-dependent `warnings`, and that one image renders its alt text. Every OTHER subresource position still hard-rejects. The cap on imports per publish is checked hook-or-no-hook, so `/api/preview` — which never fetches, and answers `image_not_previewable`/`pdf_not_previewable` BY NAME — still agrees with publish.
  - **`/assets/<sha256 of the canonical url>` IS THE ADDRESS, AND ITS THREE DEFENSIVE HEADERS ARE THE POINT** (`app/assets/[hash]/route.ts`). An imported SVG is MARKUP, and the spike measured a top-level navigation to one served plainly reaching this origin's storage and cookies — so the response carries `Content-Security-Policy: sandbox` (an opaque origin), `Content-Disposition: attachment` (a download, not a page) and `nosniff` (held to the type sniffed from the bytes at import). None of the three touches a subresource load: an `<img>`, a `<link rel=preload>` and an `@font-face` all still use these bytes (`scripts/gate-web-assets.mjs`, a real browser). The ONE exception is `application/pdf`, `inline` with a filename taken from the source URL's last segment — `attachment` cost that tier its entire feature (opened from inside a document's sandbox it produced neither a popup nor an observable download), while `sandbox` — the actual defence — is kept. Unauthenticated by construction: the bytes are a copy of a public URL and the address is derived from it, and a served document has an opaque origin that sends no cookies. `refresh_asset` (`POST /api/artifacts/assets/refresh`, `{id}` for every URL a document names or `{url}` for one) re-fetches and REPOINTS the row; it never IMPORTS (`not_cached` — a refresh door that imported would be a fetch primitive under another name), and the `url` form is deliberately unowned, because a global cache has no answer to "whose URL is it".
  - **A URL A READER COMPUTES IS IMPORTED ON FIRST VIEW** (`app/a/[id]/assets/route.ts`, `GET /a/<id>/assets?u=<url>`). Publish imports every URL a document NAMES; it cannot import the ones that do not exist until somebody is reading — a bound `<img src="$pick">`, a `src="https://…/{$pick}.png"` a pick completes, a `kind:"image"` DataTable column, a line of author script. Why it is not an open image proxy, and why it is per-DOCUMENT: (1) the document must exist and be READABLE by this caller — a uniform 404 answered BEFORE any fetch, so an id cannot be probed; (2) a per-document hourly fetch ATTEMPT allowance; (3) the SSRF guard, its DNS lookup re-run per redirect; (4) image-only, decided by the BYTES; (5) the byte cap, streamed and destroyed at it. The upstream body is NEVER returned — the answer is a 302 to `/assets/<hash>`, or the same address as JSON under `Accept: application/json`, which is how the PAGE relays for a framed document that cannot present a session (`mx:asset` / `mx:asset-result`; the exporter's key rides on `assetsUrl`). A PRIVATE document with a bound `src` therefore keeps its parent page (`declaresLiveData` — `hasBoundSource` is the third reader interaction that reaches the server, and the only one that lives in the BODY). Honest limits, one clause each: the hourly bucket is keyed on the DOCUMENT alone, so one stranger can spend it for every other reader of a public document (cache hits still serve above it); the cache-hit fast path is a cross-document existence oracle, which is inherent to the GLOBAL cache rather than to this endpoint; a validated `?$pick=` selection is threaded into the CAPTURE run, so `GET /a/<id>/export?$pick=<their url>` lets a stranger drive one import on the OWNER's charge, inside exactly those five bounds; and the byte quota is a read-then-store with no reservation, so N concurrent publishes overshoot by N × the cap rather than by one.
  - **THE MAPPED `<img>` IS THE ONE THE READER PAYS FOR** (milestone 4, `lib/story/asset-url.ts` + `lib/story/ref-data.ts`, which share `IMAGE_SIZES` so the two image paths cannot disagree). The address never moves — a stored document names the URL and every rendering derives the address from it — so the CACHE KEY moves instead: `?v=<first 8 hex of the row's object key>`, emitted whenever the caller holds a ROW (a PREDICATE lookup carries neither `?v=` nor a `srcSet`, which is why the editor's own mid-edit push emits the bare address and costs the owner one refetch per session). `refresh_asset` repoints the row, the next render emits a new `?v=`, and the route ignores `v` entirely. Beside it: `loading="lazy"` + `decoding="async"` on every mapped `<img>` past the first TWO images in document order (measured: `lazy` also suppresses React's own `<link rel=preload as=image>`); ONE narrow variant at **1280 px** for a source wider than **1536**, offered as `srcSet` — React's spelling, settled by rendering through the real SSR bundle, because lowercase `srcset` reaches the DOM unrecognised and the phone preloads the desktop copy — and served at `?w=1280` on the same address, `w` naming a width we STORED so anything else is the full copy rather than a failure. 1280 because a browser picks by SLOT × DPR: 640 was reasoned from "a phone is 390px" and every phone at DPR 3 skipped past it. The CAPTURE (`chrome=0`) is one flag and the exception: full variant, eager, no `srcSet`/`sizes` — a `sizes` hint against a headless viewport is how an og card ends up showing the narrow copy. The upload door SNIFFS (`storeImageContent`, the same `sniffImageType` the URL importer always used) and the sniffed type WINS: a PDF sent as `data:image/png` used to answer 201 and serve as `image/png` under `nosniff`, and an SVG sent as `image/png` was rasterised.

- `lib/artifacts.ts` — all artifact SQL; every read/write ownership-scoped through a `TokenActor`: a token claimed by an account acts **account-wide** (`user_id` scope — any of a user's tokens reaches anything the user owns, which is how a second agent picks up a document the first one created), an anonymous token reaches only what it created (`token_id` scope). - **A FORK IS RE-PUBLISHED AS THE FORKER, NOT ROW-COPIED** (`lib/artifacts.ts forkArtifact` — TWO doors over it and no second implementation: `POST /api/my/artifacts/<id>/fork`, which a person clicks, and the `fork_artifact` OPERATION at `POST /api/artifacts/<id>/fork` + the MCP tool, which an agent calls). Reach is READ, never ownership — the point is adapting someone else's public document — so the miss is the uniform 404 for an id that is unknown AND for one this viewer may not read, and an anonymous browser is refused separately (`409 sign_in_required`: a fork needs an owner, never a silent anonymous copy). Re-publishing is the whole design: refs resolve through `refLoaderForActor(the forker)`, so a document whose `<Mutation>` writes the ORIGINAL owner's dataset, or that reads their private image, is refused BY NAME at this door (`400 invalid_refs`, passed through verbatim) instead of being copied and then failing every write at run time — `writerFor` resolves as the document's owner, which the copy no longer is. Content travels (format, title, description, visibility, `access`, the whole meta, and the object-store bytes by REFERENCE, since every key is content-addressed — a fork of a 27 MB sheet costs no bytes); the ORIGINAL'S LIFE does not — version history (the copy is version 1 with its own genesis edit), comments (every `data-annotation-anchor` stripped through the pure `lib/annotation-anchors.ts`, which exists so the fork can strip anchors without importing `lib/annotations`, which imports this module), shares, and its placement. `link_role` and `forked_from` ride `createArtifact`'s creation-only argument, deliberately not fields on `ArtifactInput`, which the replace path shares: provenance is written once and never updated, and carrying the tier while resetting the role the LINK grants would be incoherent. `forked_from` takes no foreign key — deleting the original must not delete the copy — and NULL is "authored here", which every pre-column row already is: that equivalence is the whole migration. - **MULTI-USER EDITING — A SHARE CARRIES A ROLE, AND IT IS ORTHOGONAL TO VISIBILITY** (`artifact_shares.role`: `viewer` | `commenter` | `editor`; `ShareEntry`, `roleFor`). `visibility` is who may read via the LINK; a share is a named PERSON (by email, so an invite can predate the account) and what they may do — under every visibility, which is what lets a public document have editors at all. Four relationships to a row, decided ONCE by `roleFor(row, actor)` (`lib/artifacts`, wrapped for a request by `lib/viewer`): `owner` (everything), `editor` (reach + in-place edits, `PUT`, revert, history, the agent prompt — never delete, share, move or open writes), `commenter` (read + annotate, never edit), `reader`. The seam is `Scope`: a predicate builder with two constructors — `ownerScope` (today's rule) and `editorScope` (owner OR an `editor` share matched THROUGH `users.email`, so a collaborator's CLAIMED bearer tokens edit too, and `/docs/llm` needs no new vocabulary) — and every scoped statement names which it holds. The miss is the uniform 404 either way. `canReadArtifact` matches a share by the session's email OR the account's (`users.id`), which is what lets an invited person's agent READ what its person may. **Refs resolve as the DOCUMENT's owner, never the writer** (`writerFor(head)` at both write doors — `applyEditScoped` and `replaceArtifactFromRequest`, which loads the row BEFORE it parses): an editor's write to a document carrying its owner's `<Mutation>` or private image would otherwise fail on assets they could never own — the two exact failures a planning spike reproduced. Every write stamps `actor_user_id`/`actor_token_id` on the head, the edit log and the archived version, so history says who (`VersionSummary.by`, a handle never an email) and the live frame carries `by`. The shell carries a ROLE, not a bool (`ArtifactShell role=`, `useArtifactRole`/`useArtifactOwner`/`useCanEditArtifact`); the app server hands anyone with a role — editor or commenter — the shell, since only a plain reader is served the document top-level. There is deliberately NO invite email or accept flow: rows are email-keyed and the product already works by handing someone a link. Guarded by `__tests__/collab-editors.test.ts` (both credentials, every door, the ref-resolution cases) and `scripts/gate-collab-edit.mjs` (two logged-in contexts on one public document, no reloads; demotion refused on the next flush).
- **Concurrent editing** — agents and humans write the same document at once, with no save button.
  - `lib/story/splice.ts` is the whole conflict algebra, PURE (no DB, no DOM): an edit is a splice, its *touched span* is the innermost node it falls strictly inside, and two edits are unrelated (both apply) iff their spans don't overlap. Offsets shift; ancestry is automatic because parent spans contain children's. **`normalizeSplice` is load-bearing**: a prefix/suffix diff is minimal in length but arbitrary in POSITION, so an equivalent splice can land inside a closing tag and expand to the whole element — it slides the splice through its equivalence class and keeps the narrowest span.

The editable host carries the same lesson: it reports its props equal while it HAS FOCUS, which is how in-progress typing survives an upstream re-render — and was also how an agent's write could not reach the paragraph the cursor was parked in. It bails out only while the BODY is unchanged (`bodyEpoch`).
- **Editing a chart** is a PROP edit, not a new kind of edit: clicking a `<Question>` reports an EMBED selection (its own channel and `data-mx-embed-selected` stamp — a component can never be a *format* target, its chrome is render output), and `VizEditorPanel` is a pure lens over that node's `data`/`viz`, writing back through `updateQuestionChartInJsx` on the same queue as everything else. Two things are load-bearing: the selection is **held by the editor, not the body** (a chart edit re-parses the body, so a selection living there would clear itself on the user's first change), and it is **dropped whenever the document is replaced from outside** (remote adopt, restore, code mode) because AST paths are POSITIONAL — a shifted path can name a *different* `<Question>`, which no tag guard downstream would question. The binding picker lists the tables the DOCUMENT declares (`lib/story/table-catalog.ts`, derived from the source + the last dataflow state — never fetched); the canvas is seeded with the page's server-run dataflow and re-runs a DRAFT's queries through `POST /api/query` when its declarations change (keyed on the declarations, not the text).

## Agent evals (`evals/`)

**Coding harnesses × models, publishing to THIS product, compared side by side** — the minusx QA measured-flows
system (`test/qa/metrics.ts` + `scripts/qa-report.ts` + `deploys/qa-eval.yml`) ported to a product whose agent is an
EXTERNAL process. Rows are the minusx `MetricRow` schema unchanged (`number | pass | image | text`, images in a
laptop/mobile × export/playwright matrix), one run directory per run, `report-<UTC stamp>.html` self-contained (named by when its runs started, so two downloads never overwrite each other). No LLM judge,
no repeats, no delta math, no pixel diff: deterministic rows and a human comparing image rows. The `agent-smoke`
job in `ci.yml` runs the CI task set on one cheap agent it names itself, toggled by the repository VARIABLE
`AGENT_SMOKE_ENABLED` (a skipped job satisfies a required check); the comparison matrix runs from
`deploys/artifact-eval.yml`. Provider keys live in the main `.env`, named on the command line, never committed;
the driver strips `*_API_KEY` from the product server's environment.
- **This repo runs ONE leg and knows NOTHING about the roster** (`lib/leg.ts`): `--harness`, `--model`,
  `--api-key-env`, `--label` and the price rates describe it entirely, and a run writes ONE directory. Which
  agents exist, which to compare, and what a set of them is called are DEPLOYMENT concerns — the workflow owns
  the roster and the matrix, and `eval:report` merges N run directories without knowing why there are N. minusx
  draws the line in exactly the same place: the word "leg" appears only in its deploys workflow, never in the app
  repo. Getting this wrong first time produced ids like `cc-opus5` and a "control" set that broke the
  one-model-per-harness rule (Claude Code ↔ Anthropic, Codex ↔ OpenAI, Pi ↔ DeepSeek, OpenCode ↔ MiniMax — each
  agent is the harness its users actually hold, running a model that harness is native to). A price is passed in
  rather than looked up, so an unpriced run reports cost as UNKNOWN rather than as zero. The key is named by
  VARIABLE, because an identifier containing "apiKey" makes CodeQL read the variable's NAME as a credential and
  flag the error message that names which key to set.
- **MODE IS THE CROSS-PRODUCT OF TWO REAL AXES** (`lib/mode.ts`): where the skill comes from
  (`fetched_skill` or `installed_skill`) and how actions happen (`api_action` or `mcp_action`). The four accepted names are
  `fetched_skill+api_action`, `fetched_skill+mcp_action`, `installed_skill+api_action`, and `installed_skill+mcp_action`; the last is the full plugin. The
  compiler selects the matching skill too: fetched delivery can serve either the API/curl rendering or
  `?transport=mcp`, while installed delivery materializes either rendering with local `references/`.
  A task never overrides the mode's transport. Pi preserves the requested skill source but substitutes
  API actions when MCP was asked for, because Pi has no MCP client, and the report names that substitution.
- **The FILENAME decides which set a task is in** (`lib/task-set.ts`), the way minusx marks its measured flows
  `*.eval.spec.ts`: `tasks/<id>.eval.json` is a comparison column — one brief per product template (`deck`,
  `dashboard`, `report` → `editorial`, `scrolly`, and `comment-image`), deliberately DIFFERENT KINDS of document, because a report whose image rows all show the
  same-looking prose page is not a comparison. A plain `tasks/<id>.json` is CI-ONLY (`comment`, `data`, `edit`, `mcp`): a
  product guard with one right answer, which six legs re-answering buys nothing. The sets are DISJOINT — running
  the creative briefs per pull request would spend minutes and dollars re-answering a question that is not a
  regression. Tasks carry an `order` so the report follows the template sequence.
- **A TASK HAS A KIND, AND THE KIND OWNS ITS SEAM** (`lib/score/kinds/`: `contract.ts` states it, `publish.ts` is the default, `comment.ts` is the first one that needed it). A kind owns three things that were three conditionals in `main.ts`: the CHECK NAMES it may answer, the driver-side SETUP its task needs before the agent runs, and the product-side CHECKS that grade it — so `main.ts` asks the registry and stays a driver. `prepareTask` runs setup BEFORE the `published` baseline is read, because a comment's anchor stamp is a REAL edit (it bumps the version and rewrites the stored markup) and a baseline taken after it would make `published` true for a document the agent never touched. A driver step that fails is a `DriverFailure` naming the STEP, reported as `setup_ok: false` / `checks_ok: false` with the step in `first_error` and every one of the kind's checks left `null` — because the driver's own calls carry `DRIVER_HEADER` and are invisible to the ledger, so without a name a broken seed reads as "the agent did nothing" and a failed thread read as "the agent ignored the comment". `comment-image.eval.json` is the kind's comparison column: a seeded document, a seeded comment asking for two pictures BY URL ("use the URLs as they are"), and `urls_kept`/`assets_served`/`assets_ok` beside `responded`/`resolved` — one task that exercises the whole batch end to end. Measured, both 1/1 first try: opencode × minimax-m3 (the model `agent-smoke` runs) **$0.011 / 31 s**, Claude Code × Opus 5 **$0.24 / 47 s** — cheap enough that the comment task joined the CI row.
- **NEVER `git add -A` IN A TREE THAT HAS RUN AN EVAL.** A run writes a `.metrics` directory, a product server's object dir and a PGLite dir, and the transcript it captured holds the agent's whole session — `.gitignore` covers the run directories, and staging by NAME is what makes that a belt beside braces rather than the only one. The provider key is read from the tree's `.env` by the driver, registered as a secret and stripped from the product server's environment (`PROVIDER_KEY = /_API_KEY$/`); it must never reach a commit, a report or a pasted log.
- **Only the checks a task LISTS gate it** (`lib/score/verdict.ts`); every other check the scorer computed is
  recorded for the reader. A scorer that gates on everything it can measure turns information into noise:
  `canonical_stable` false means the product hoisted a mid-document `<Helmet>` (the product working), and a harness
  that fell over AFTER publishing still produced the document — `harness_ok` records that without failing the run.
- **A provider key must not reach a log, a transcript, or an error** (`lib/secrets.ts`): the key travels to the
  harness in its environment, and three things read that environment back — the harness's stdout (the transcript
  CI uploads as an artifact), its stderr, and the CLIs themselves, since `codex login` rejects a bad key by
  echoing it and `codex.prepare()` puts that stderr into the Error `main()` prints. All three are scrubbed;
  a stream holds back the longest secret's length so a key cannot straddle two chunks. Found by CodeQL
  (`js/clear-text-logging`), and the path was real, not a false positive.
- **A run can target a LIVE DEPLOYMENT, and that needs the OPPOSITE proxy** (`lib/mitm.ts`, `--deployment`): a
  server this driver boots mints its links from whatever Host it is asked on, so a reverse proxy can simply BE the
  base URL. A deployment cannot — a live deployment answers a foreign Host with a 307 to its login page, and then
  mints links pointing at itself, walking the agent straight past any reverse proxy. So the agent is put in a
  PROXIED ENVIRONMENT instead (`HTTPS_PROXY` + a CA it trusts) and handed the deployment's own real link:
  intercepted by where it SENDS rather than by what it is TOLD to ask for. Only the host under test is decrypted;
  every other host blind-tunnels, so provider calls never cross the TLS termination or enter the ledger. Two things
  are load-bearing: `SSL_CERT_FILE`/`CURL_CA_BUNDLE` REPLACE the trust store rather than adding to it (a bundle of
  our CA alone made every real certificate untrusted — Codex died on `UnknownIssuer` reaching OpenAI), so the
  bundle is the system roots PLUS ours, while `NODE_EXTRA_CA_CERTS` is additive and takes ours alone; and the raw
  socket must be handed to the TLS server for it to do the handshake, since a hand-built `TLSSocket` skips SNI and
  never completes. Verified against all four harnesses.
- **Two handoffs, both the product's own** (`lib/tasks.ts`): `start-link` passes on the exact line a human pastes,
  so the TOKEN goes to the agent and the driver never holds it; `token` is for tasks the driver must set up first
  (seed a document to edit, write an MCP config), where it spends the start link itself. A leg with
  `vision: false` gets one added line — the docs teach `GET /a/<id>/export`, an agent fetches that PNG to
  check its own work, and a text-only model's harness then 400s on it (DeepSeek V4 Flash, found by running it).
- **Per leg one prod server; per TASK one recording proxy — and the agent must only ever see the proxy.** The server is
  `dist/proxy-server.mjs` (`lib/server.ts`: in-memory PGLite and its own object dir); the recording proxy
  (`lib/proxy.ts`) appends one JSONL line per request — status, timing, UA,
  bearer presence, the `error` code of a JSON failure, and the markup sent/echoed on document writes. **One ledger per
  TASK** (`runs/<task>/ledger.jsonl`), which is what lets a leg's tasks run AT THE SAME TIME (`run.concurrency`,
  default 4, via `lib/pool.ts`): the driver's own setup calls are marked (`DRIVER_HEADER`) and skipped, so the file
  holds exactly that agent's traffic and nothing needs to know when it ran. It was one ledger per LEG sliced by a
  wall-clock window, and that window was the only reason tasks ran one at a time — a shared file attributed by time
  mis-scores silently the moment two overlap. It also cost a real run: production's `claude-code` leg was CANCELLED at
  the job's 60-minute ceiling with four tasks summing past it, and a leg's wall time is now its LONGEST task, not the
  sum. A task's own failure is caught and scored `false` rather than rethrown — rejecting would tear the shared server
  down under siblings whose agent time is already paid for. That ledger IS
  the protocol score (`lib/ledger.ts`: write attempts, first error, read-docs-before-write, `canonical_stable`) — the
  product's analytics `client` column is UA-only and cannot attribute a run. Two things were learned by running it:
  the product builds every link from the request Host (`lib/http.ts baseUrl`), so the start document is minted
  THROUGH the proxy and the proxy forwards Host unchanged (rewriting it handed the agent the server's port and the
  first leg made zero proxied requests); and the driver never holds the agent's token — the start link hands it to
  the agent — so product truth is read from the SERVED document (`/a/<id>/raw?chrome=0`), not the owner API.
- **Harness adapters are pure `invocation(ctx)` + `reduce(stdout)` pairs** (`lib/harness/*`), pinned by tests
  against the REAL event streams each CLI produced (`__tests__/fixtures/`). What each one hides: Claude Code runs
  `--bare` (needs an API key, no keychain) and reports an API error as `is_error: true` with `subtype: "success"`;
  Codex ignores `OPENAI_API_KEY` in a fresh `CODEX_HOME` (`prepare()` runs `codex login --with-api-key` from
  stdin), reads stdin unless it is closed, and its `workspace-write` sandbox DENIES NETWORK by default (both its
  tasks ended after one turn with zero HTTP calls until `sandbox_workspace_write.network_access=true`; and on
  GitHub's ubuntu-24.04 runners its bubblewrap sandbox cannot launch at all under AppArmor's user-namespace
  restriction — EVERY shell command fails with exit 1 and no output, `rg --files` and `curl` alike, so it fell back
  to provider-side web search for whole runs and scored 0/4 on production three times, until the deploys workflow's
  sysctl step, the same one openai/codex-action runs); Pi exits 0
  on a model error (`stopReason: "error"`) and ships NO MCP client, so an `mcp_action` mode preserves the skill
  source but substitutes `api_action` and reports it; OpenCode can exit before its final `step_finish` (telemetry unavailable, NOT a failed
  run) and re-emits a text PART as it grows, so its reducer keys parts by id. **Cost is the HARNESS's own figure
  first** (`lib/price.ts taskCost`, `cost_source` row): each harness prices its run against the provider it is native
  to, cache discounts included — Claude Code's matched a hand-priced run to 0.1%, Pi's matched LiteLLM's table to the
  cent — and the hand-typed roster rates were the thing that was wrong (2–3× on the Fireworks legs). Tokens × the
  leg's rates is the fallback for Codex alone, which reports no cost: OpenAI counts cached AND cache-written tokens
  INSIDE `input_tokens` (subtracting only cached billed every write twice), and bills a provider-side `web_search`
  per CALL — counted from the transcript and priced by `--price-web-search`, since no usage object carries it.
  Roster rates in deploys are read off LiteLLM's price table, never typed from memory.
- **A streaming harness must be filtered at the LINE, not summed at the end** (`HarnessAdapter.keepLine` +
  `lib/spawn.ts`): Pi's `--mode json` re-sends its whole partial message on every token, which is quadratic in the
  document being authored — one real run left a 541 MB transcript and died with EPIPE. Adapters drop their own
  firehose (Pi `message_update`, Claude Code `stream_event`), and a byte cap keeps the TAIL in memory (a reducer
  reads the end) and the HEAD on disk (a person reads the start).
- **The dataflow runs on the SERVER, so `query_ran` reads the island, not the wire** (`dataflowRows`): a static
  document never calls its own `/query` endpoint — that happens when a `<Value>` changes — so waiting for the
  request waits forever. The rows the server produced ride in the document's JSON island, and that is the
  evidence a `<Query>` ran at all.
- **The PRODUCT says whether the work happened; the LEDGER says how well the protocol was used.** `published`
  used to read `successfulWrites > 0` counted from the proxy, which made "did the agent publish" depend on whether
  the write crossed THIS machine — and it does not always: codex reaches a public deployment through OpenAI's own
  server-side browsing tool, leaving an EMPTY ledger for a run that made real requests. So `published` is now the
  served document compared against the start document as served BEFORE the agent ran (`baseline`) — the start
  document is not blank, it serves "Untitled / Waiting for your agent…", so "has content" cannot tell a written
  document from an untouched one, and the served body is byte-stable between reads. When the ledger saw NOTHING
  (`LedgerMetrics.observed`), every judgement it makes is `null` rather than `false` — `read_docs_before_write:
  false` asserts the agent skipped the docs when the truth is that we could not watch — and `gatedChecks` drops the
  ledger-only checks from what may DECIDE the run, so the verdict rests on what was produced. Nothing about the
  agent is inferred from the reach of our instrument.
- **Score the artifact the agent ACTUALLY wrote** (`scoredArtifactId`: the LAST link in its own answer, then the
  ledger's last write that was not later DELETEd, then the start document), never simply the one the start link
  named: Claude Opus 5 ignored the start document and `POST`ed two of its own, and the scorer read the untouched
  original and reported a titleless failure for a document that was never written. The order was learned twice more:
  the ledger came first once, and Opus 5 creates a SCRATCH document, exports it to look at its own rendering and
  deletes it — the ledger's last write, a 404 to score — while its answer named the real one; and an agent lists what
  it tried before ending with the deliverable, so the first link in a message is the wrong one. `used_start_document`
  records the divergence.
  For the same reason a 404 is only counted when the path matches no route the docs teach (`isKnownRoute`) — a
  `DELETE` of a missing artifact is a missing RESOURCE, not an invented endpoint.

## Conventions (ported from the minusx house style)

- **Deep modules**: a feature's complexity belongs in ONE cohesive `lib/` module with a narrow interface; route handlers only translate lib results into HTTP codes. Prefer deepening an existing module over adding a shallow new one.
- **No inline/dynamic imports** — import at the top of the file. (Sanctioned exception, documented inline: the engine-selecting imports in `lib/db.ts`.)
- **No `process.env` outside `lib/config.ts`.**
- **No explicit key re-enumeration** — spread typed objects instead of re-listing fields.
- UI tests locate elements by `aria-label` only; every interactive element gets one.
- **Tooltips use `components/Tooltip.tsx` everywhere in app chrome** — and the story registry imports the SAME module, which is why it does not live in `components/kit/`: that directory is the story component layer, and the reader graph is not allowed to reach it (`lib/__tests__/reader-bundle-hygiene.test.ts`, which the annotation work turned red by importing the tooltip from there). It composes `clsx`/`tailwind-merge` directly for the same reason. They portal by default so fixed, transformed, and overflow-hidden ancestors cannot clip them; use `positioning.placement` for edge controls. Never use the native `title` attribute for tooltips — it's slow and unstyled.
- **A MERGE GATE NEVER DEPENDS ON A THIRD PARTY BEING UP** (`scripts/lib/sheets-stub.mjs`, loaded by `scripts/gates.mjs` with `--import` for the throwaway servers IT boots, and by nothing else). `gate-data-ingest` imports Google's OWN public sample sheet to prove the whole stack — Sheets link → export URL → CSV → inferred columns → stored rows → a chart drawn from them — and on 2026-09-04 Google would not serve a GitHub runner, twice, the retry-alone included: a red merge gate for a sheet that was fine. So the URL stays exactly as an author writes it and the ANSWER is local; the gate file is untouched. The scope is the point: it matches `docs.google.com/spreadsheets/` and delegates everything else, and it patches `globalThis.fetch` — which `lib/data-ingest/sheets.ts` calls — while `lib/web-ingest/fetch.ts` uses `node:https` with its own DNS lookup, so the SSRF-guarded door cannot be stubbed by accident (asserted, not assumed: `scripts/__tests__/sheets-stub.test.mjs`). It also DETERMINISES the refusal leg, which used to borrow Google's 404 for a made-up id. What it gives up is the live contract — that Google still answers `text/csv` — and that belongs in a scheduled canary, never in a check that can block a merge. Beside it: **Google refusing us is not the author's sharing settings** — a 429 or 5xx is now `fetch_failed` naming the status, where every non-CSV answer used to be `sheet_not_public`, sending someone to fix a share setting that was never wrong (403 stays `sheet_not_public`, which is what a private sheet answers).
- **Test accounts are named `mxmx_test_*`** — every browser gate mints its login email as `mxmx_test_<gate>_<ts>@example.com`, so the account (and its auto-assigned handle) is identifiable as disposable wherever it lands. A gate run against a SHARED environment leaves users behind; this is what makes them safe to prune later without guessing which are real.
- **A local login code is read from the protected development outbox, never from an app endpoint.** `npm run dev` writes outgoing local mail to `.artifactbin/dev-mail.jsonl` and prints the OTP for a human; `npm run dev:otp -- <email>` lets a coding agent retrieve the newest unexpired code even when somebody else owns the server terminal. Browser gates give their throwaway servers one per-run outbox and read by exact recipient, so parallel logins cannot steal each other's code. Public origins always use Resend's fixed API endpoint.
- Keep tests calling the real route handlers in-process (no mock HTTP layer) against in-memory PGLite; reset state in `beforeEach` (`resetRateLimit()`, wipe tables).
